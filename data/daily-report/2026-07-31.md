## Findings

### 1. The merge pass did not run — and this time the schedule itself never fired

Yesterday's fix replaced the agent with `.github/workflows/merge.yml` (cron `0 11 * * *`, 11:00 UTC =
07:00 ET), merged to `main` at 12:47 UTC on 07-30. Today's 11:00 UTC slot was its **first scheduled
opportunity**, and it did not take it.

The Actions history is unambiguous — `merge.yml` has **exactly one run in its lifetime**:

```
run #1   event: workflow_dispatch   2026-07-30T12:47:41Z   conclusion: success
```

That is yesterday's manual test. **No `schedule` run was ever created** — not queued, not failed, not
cancelled. As of 12:06 UTC the slot is 66 minutes past.

This is not the same failure as yesterday. Yesterday an unattended agent could not perform the merge
write from the cloud container. Today the mechanism that replaced it is correct — it self-tests, it
holds `MERGE_TOKEN`, and it worked when dispatched by hand — and the *trigger* is what is missing.
Two causes are worth checking in order, and only the first is benign:

- **GitHub delays or silently drops scheduled runs under load**, particularly on the hour. If that is
  all it is, tomorrow's slot fires and nothing needs doing. But it cannot be assumed twice.
- **The repository's scheduled triggers are not active for this workflow.** The manual dispatch proves
  the job is valid; it proves nothing about the `schedule:` event.

A one-command test settles it, and it is in decision 1 below.

### 2. `daily-merge` can no longer be verified by log shard at all — the roster now watches for a file nothing writes

`daily-report.js` decides a routine ran by looking for its shard in `data/routine-log/`. The merge
pass no longer writes one: `merge-run.js` mentions `data/routine-log/` only as a path pattern in its
source whitelist and as a self-test fixture, and never appends a line. The two shards on `main`
(2026-07-29, 2026-07-30) were both written by the **agent** it replaced, the second by hand (#273).

So from yesterday forward the `daily-merge` row reads **DID NOT RUN every single day, including days
the Action runs perfectly.** Today that verdict happens to be correct, which is exactly what makes it
dangerous — the row will look identical tomorrow whether the pass fires or not. The authoritative
signal for this routine is now the Actions run history, and nothing reads it.
