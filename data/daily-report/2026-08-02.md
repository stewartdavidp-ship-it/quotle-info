### 2. The merge pass already loops. What breaks it is that it believes a stale answer

Yesterday's decision 1 proposed *"have `merge-run.js` loop — merge, wait, rebuild — inside one run."*
**It already does.** `tools/merge-run.js` runs a 12-round loop; each round asks the gate and merges
one `MERGE`, and it exits only when the gate returns none:

```js
for (let round = 0; round < 12; round++) {
  const decisions = gate();
  const next = decisions.find((d) => d.verdict === 'MERGE');
  if (!next) { /* …rebuild the stale ones, then */ break; }
```

So the loop is not missing. What ends it early is that GitHub invalidates `mergeable` on every open PR
the moment something lands on `main` and recomputes it asynchronously — and the pass re-asks inside
that window, gets an answer that is not yet true, and treats it as final. **The bug is the absence of
a re-poll, not the absence of a loop.** That distinction changes what needs building.

Today the same window produced the opposite error, which is the clearest evidence yet. The pass's
closing gate report, taken 22 seconds after the merge, said:

> `MERGE    #286   reports/2026-07-30-close   green, in scope, up to date`
> `MERGE    #288 … MERGE #289 … MERGE #292 … MERGE #299 … MERGE #300`
> `=> 6 to merge, 0 needing a rebase+rebuild, 4 left alone`

Six minutes later the same gate calls **all six of those** `REBUILD — behind main`, and the three it
had filed as `WAIT` are the genuinely mergeable ones. The closing report was inverted. Yesterday the
window returned all-`null` and the pass rebuilt nothing; today it returned stale-`clean` and the pass
reported six merges available that did not exist. One defect, two faces.

**Credit where due:** today's run did both halves — merged #296 *and* rebuilt #297, #301, #302, which
are now the three green ones. The rebuild path works. The arithmetic is still losing: one merge per
run, one run per day, three or four PRs arriving per day.
