## 5. Findings

### 5.1 The traffic outage is an egress denial, not a GoatCounter setting — item 43 has been wrong for 23 days

`node tools/traffic.js` prints, as it has since 2026-08-28:

```
traffic.js: 403 from GoatCounter — the dashboard is no longer public.
Fix: GoatCounter -> Settings -> "Dashboard viewable by" -> Anyone.
```

**That diagnosis is unearned in this environment.** `tools/traffic.js:61` routes *any* `403` or
`401` into that message — including a `403` from the egress proxy, which never reaches GoatCounter
at all. Today the proxy's own log says exactly that:

```json
{ "kind": "connect_rejected",
  "detail": "gateway answered 403 to CONNECT (policy denial or upstream failure)",
  "host": "quotle.goatcounter.com:443" }
```

A direct `curl` to `https://quotle.goatcounter.com/` from this container fails the same way
(`connect_rejected`, exit 56) before any HTTP request is sent. So the request is being refused by
the container's network policy, and `traffic.js` is reporting a GoatCounter setting change it has no
evidence for. (`daily-report.js` takes a different path and reports the same host as
`traffic: fetch failed`, which is at least honest about knowing nothing.)

**This does not prove the dashboard is public** — it proves the check has never reached GoatCounter
from a cloud routine, so the dashboard's state is simply **unknown**, and twenty-three days of
"flip the dropdown" rest on a message that cannot distinguish the two. The cheap way to settle it is
one command on the operator's own machine, unproxied: if `node tools/traffic.js` prints a figure
there, item 43 was never real and this is item **13** (egress allowlist) wearing a different hat.

This also amends item **86** (added 09-18: *make `daily-report.js` carry the traffic tool's own error
string*). Shipping that as written would propagate the **wrong** string into the report. 86 should
carry the underlying cause instead, and `traffic.js` should stop asserting a remedy it cannot
support.
