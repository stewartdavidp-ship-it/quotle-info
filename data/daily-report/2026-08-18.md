## 3. Findings

### F1 — Two passes independently found the same `creditedTo` defect, and both hand-worked around it

This is today's headline because it was reached twice, from different directions, on the same day.

The **daily wave** (#541), in its own words:

> **`prep-wave.js` cannot stamp `creditedTo` on the disputed-EQUAL case the README requires.**
> `README.md` says a disputed record whose author *is* the magnet must be stamped, because
> `rightPersonWrongWords()` gates on `primaryCredit()` being **equal** to the hero name. But
> `prep-wave.js:~200` stamps only when `leadName(rec.answer.authorName) !== leadName(b.author)` — and
> the accent/entity folding added to make that comparison correct is precisely what now makes the
> equal case fall through. So the rule and the tool disagree, and the tool wins silently: this wave
> reported `creditedTo stamped: 0`. I stamped `whatever-the-mind-of-man…` by hand.

Its suggested fix: *"stamp when `confidence === 'disputed'` regardless of name equality, keeping the
existing withhold for `verified`/`attributed`."*

The **r38 wave** (#538/#539) reached the identical rule from the other side, and settled the third
case the runbook never covered:

> `rightPersonWrongWords()` (`tools/template.js:2054`) gates on `q.confidence === 'disputed'`
> **explicitly**, so the stamp rule is a confidence test, not a name test.

r38 stamped 7 disputed by hand and deliberately withheld 32 (`verified`/`attributed`), because
*"a stamp buys no better rendering; it would only assert a false credit against a page that credits
that person."* Two passes, one conclusion, one hand-stamp each. The rule is now fully specified —
it just is not in the tool.
