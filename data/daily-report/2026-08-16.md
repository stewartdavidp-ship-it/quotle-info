## Findings

### 1. Preflight exception (b) caught all four passes again — and nothing changed, because nothing was fixed

This was yesterday's decision 2. It is unactioned, so it fired again on the wave, the reports pass,
the review pass and this one — four for four, two days running. The tree was **28 commits behind**
for the three night passes and **31** for this one.

The review pass (#511) gave the sharpest diagnosis yet, naming the precise reason the check does not
protect you:

> *"`git checkout main` moved the tree **backward 28 commits**. At session start HEAD was already *at*
> `origin/main`; the stale ref was the local `main` pointer, which passes `local main sane` because
> 'sane' only means *ancestor of* `origin/main` — and a 28-commits-behind ref is a perfectly good
> ancestor. […] The premise holds only when local `main` is *level with* `origin/main`, not merely an
> ancestor of it. Exception (b) has no guard for the gap."*

The reports pass (#510) added the shape of the start state:

> *"this container did not merely start 'off the branch' — it started detached at the current tip with
> a stale `main` ref behind it. The working tree was already current, which is why `tree clean` and
> the doc-read were unaffected."*

The wave (#509) reached the same place and drew the same line about scope:

> *"Exception (b)'s own remedy moved the tree onto a stale local `main`, which is precisely the
> failure mode exception (a) warns `git checkout main` can cause. […] **This is not mine to encode** —
> `tools/` and `workflows/` are untouched by this PR."*

All three flagged rather than edited `workflows/`, which is correct, and all three then improvised the
identical last step. That improvisation is the exact failure mode exception (b) was written to
eliminate. The recovery is safe every time — tree clean throughout, a fast-forward discards nothing —
but four passes a day are each doing an undocumented step to reach green.

### 4. Structured data cannot hedge, and the wave refused to fake it — escalated, not patched

> *"on two pages `Quotation.creator` names an author more flatly than the prose does — Berenda where
> QI declines to settle between him and Steve Allen, and Woody Allen where the page says the
> attribution is unsourced. **Structured data has no hedge slot.** […] Omitting `creator` would assert
> nothing at all on records whose 1,570 siblings all name one. Flagging as a structural limitation,
> not patching four records around it."*

The wave's reason for not fixing is sound and worth keeping: the visible hero, `answer.authorName` and
the JSON-LD all agree, so prose and structured data do not *contradict* each other (unlike the

This is a corpus-wide convention question, and it wants a person. It is close kin to carried decision
4 (the `Unknown` creator + `sameAs` convention) — both are "what may JSON-LD assert when we don't
know?".
