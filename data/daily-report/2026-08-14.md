### 1. NEW — the first organisational creator in the corpus ships as a `Person`, and it is live now

The wave found it, measured it, and refused to patch it. In its own words:

> `tools/template.js:277` hardcodes `Quotation.creator` as `{'@type':'Person'}`, so the League for
> Programming Freedom ships as a `Person`. Measured: this is the **first of 1,567 records** with an

> in a shared generator is one central edit and not a per-record fix, so nothing under `tools/` was
> touched. The fix pattern already exists in the same file — line 2060 does `w.authorType || 'Person'`.

**Verified end to end, in the built page, not just the source.** `tools/template.js:277` reads
`quotation.creator = { '@type': 'Person', name: s.creator.name };`, and the shipped JSON-LD at
`who-said/a-future-startup-with-no-patents-of-its-own-will-be-forced/index.html` is:

```json
"creator": {"@type": "Person", "name": "League for Programming Freedom",
            "sameAs": "https://en.wikipedia.org/wiki/League_for_Programming_Freedom"}
```

`template.js:2060` already does exactly the right thing for the *container* author
(`{'@type': w.authorType || 'Person'}`), with a comment explaining the default. The `creator` branch
never got the same treatment because until today it never needed it. **→ decision 1.**

### 2. NEW — the one page whose primary source was unreachable carries the flattest machine-readable verdict of the four

The wave fixed three of four records where *"the machine-readable verdict [was] more confident than
the page's own prose"*, using `schema.verdictNote`. The LPF page was **not** one of the three, and it
is the page the wave was least able to confirm. Its own disclosure:

> **The LPF paper was never read.** The identification rests on Wikiquote's Misattributed entry
> (which I read as raw wikitext, and which states it explicitly). […] `sourcesVerified` records the
> LPF URL with `containsClaim: false`.

**Verified:** that record is the only one of today's four with **no** `verdictNote`

Both sides are defensible — Wikiquote *does* state it explicitly, which is more than the Sykes pages

### 3. NEW — `sourcesVerified`, the field the pipeline calls "the site's #1 discipline", never reaches `main`

`workflows/generate.js:177` makes `sourcesVerified` a **required** dossier field, and `:334`
instructs the researcher:

> Populate sourcesVerified with {claim, url, containsClaim} for every source link — do NOT use a link
> unless a fetch confirmed it supports that claim (this is the site's #1 discipline).

**Verified:** `toRecord()` does not carry it through. `grep -l sourcesVerified data/quotes/*.json`
returns **0 of 1,567**; `containsClaim` likewise 0. `grep -rn sourcesVerified workflows/prep-wave.js
tools/` returns nothing. The dossier lives in the Workflow transcript's `journal.jsonl`, which is
session-local and never committed — `find . -name "gen-d*.jsonl"` returns nothing in the repo.

So the per-link verification evidence is produced, used once for the audit, and then discarded. The
consequence is concrete: today's wave re-fetched all 13 links and confirmed each against its claim,
and **none of that survives on `main`**. The next audit of these pages starts from zero, and there is
no baseline to detect link rot against. This is not a defect anyone introduced today — it is how the
pipeline has always worked — but no prior daily report has named it. **→ decision 3.**
