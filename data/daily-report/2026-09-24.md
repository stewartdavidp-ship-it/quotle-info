### 5.3 #977's site-wide "`href`" defect is refuted — no item filed

#977 reported, and deliberately did not fix:

> **A site-wide template artifact.** A literal `https://&hellip;` href appears on **all 2,263**
> pages, not just this wave's. It predates this wave and lives under `tools/`, so nothing was
> changed for it. Worth a generator branch of its own.

**The count is right and the diagnosis is wrong.** Measured against `main`: the string occurs on
**2,258 of 2,258** quote pages, exactly once each — so "every page" is correct. But it is not an
`href`. It is the `placeholder` attribute of the source-suggestion input, hand-written at
`tools/template.js:1742`:

```html
<input class="src-add-url" name="url" type="url" inputmode="url"
       placeholder="Optional: https://&hellip; a link that shows it">
```

`grep -ro 'href="https://&hellip;' who-said/` returns **nothing**. Named character references are
decoded by the HTML parser inside attribute values, so this renders as
`Optional: https://… a link that shows it` — which is what it is meant to say. Nothing is linked,
nothing is broken, and no crawler sees a malformed URL.

**The contrast with item 77 is the reason this is worth a section.** Item 77's `&lt;em&gt;` leak is
real precisely because it is *double*-escaped: the parser decodes `&lt;` to a literal `<`, so
`<em>` shows up as text in nine meta descriptions. `&hellip;` decodes to the character it names. Same
file, same attribute position, opposite outcomes. A generator branch opened on this would have
changed working markup.

The wave was right to leave `tools/` alone and right that the pattern is site-wide. **Filed as
refuted rather than carried**, so it does not accrete into the ledger as a phantom.
